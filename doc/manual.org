#+title: The Techne Manual

Techne is an editor you extend and inspect in its own Lisp while it
runs, in the spirit of Emacs. This manual says how to use it; what each
command, procedure, option and mode does is in the editor itself, where
help shows it (see [[*Help]]). Keys are shown as your profile binds them:
read here in the editor, \[find-file] is the key that opens a file.

* Starting

~techne FILE~ opens FILE in a window, ~techne term FILE~ in a terminal.
Both take ~--modal~ for the modal profile, Vim's keys; without it the
keys are Emacs's.

Edits are written to a journal as you make them. If the editor stops
before you save, the next start replays them: nothing typed is lost. A
crashed runtime is restarted at once with its files, panes and carets.

An editor running opens files for other programs, as Emacs's server
does for emacsclient: ~techne --open FILE~ (or ~techne term --open
FILE~) shows FILE in it and returns. With ~--wait~ it returns only once
you are done with the file: \[server-edit] saves it and kills its
buffer, as killing the buffer or =:wq= in the modal profile do. So
~EDITOR="techne --wait"~ edits commit messages in the editor you have
open. With no editor running, the command starts one on the file.

~techne window --attach~ opens another window on the editor running, as
~emacsclient --create-frame~ opens a frame; ~techne term --attach~ makes
the terminal one, as ~emacsclient --tty~. Each has panes, a minibuffer and
a caret of its own, over the same buffers. With a file, the window shows
it. When the window the editor started in closes, the editor runs on for
the windows attached to it, until the last closes.

Programs can evaluate code in the editor running too, as with
emacsclient --eval: ~techne eval '(message! (current-session) "hi")'~
prints what the code wrote, then its value; an error goes to stderr
with the frames it was raised in. It runs in the session you used last,
so what it shows is shown where you look; with ~--detached~, in a
session no frontend shows. ~--as NAME~ says who it runs for, as the
operation records show it, and ~--timeout SECONDS~ (10 by default)
bounds it; the editor waits for it meanwhile, and C-g stops it. So an
agent can read =*Messages*=, look at your buffers or reload a package in
the editor you have open. =*Server log*= shows what programs evaluated
and what came of it. Any program running as you can do this, as with
Emacs's server; the option ~server-eval~ turns it off.

* Screenshots and recordings

In the window frontend, =M-x screenshot= saves the next rendered editor
frame to a new PNG. It includes panes, gutters, mode lines, popups and
the minibuffer, not other applications, window decorations or the system
mouse pointer. No desktop capture permission or external capture tool is
needed. Visible sensitive text is included: capture only what you intend
to share.

Agents and other programs can capture an already running editor:

#+begin_src sh
techne window --screenshot /tmp/editor.png
techne window --record /tmp/editor-recording --record-frames 30 --record-interval 100
techne window --stop-recording
#+end_src

These commands use the editor socket under =$XDG_RUNTIME_DIR= and never
start another editor. Screenshot completion prints a JSON =Captured=
reply with =path=, =snapshot=, =width= and =height=, only after drawing and
saving succeeded. It captures the fresh snapshot answering the request,
or a newer one; the id identifies the frame actually drawn and is local
to this runtime. It does not promise that background work has finished.
An external screenshot does not change the echo area it observes.
Existing destinations, including symbolic links, are refused; PNGs are
private files, written whole before becoming visible at their destination.
GPU completion and PNG encoding run on a bounded worker, not the window
thread: typing, redraw and closing remain responsive during capture.
External screenshot requests expire after 25 seconds, or are cancelled if
the caller disconnects. Cancellation releases pending slots and prevents
late file publication, even if the editor runtime was busy. If publication
already won the race, the reply acknowledges that completed screenshot.

=M-x start-recording= records up to 100 frames in a new private directory;
=M-x stop-recording= finishes early. The CLI permits 1..300 frames and
50..10000 ms between a completed frame and the next request (defaults:
100 frames, 100 ms). There is only one recording frame in flight: slow
rendering lowers the frame rate instead of growing a queue. Recording
also ends on capture failure or after 256 MiB plus at most one frame.
An already requested frame may finish after stopping. The =Recording=
JSON reply acknowledges starting or stopping, not completion of all frames.

A recording is a PNG frame sequence, not an MP4: =recording.scm= is an
atomically updated Scheme alist with =format= (=techne-frames-v1=),
=active=, =interval-ms=, =bytes= and =frames=. Each frame records its file,
snapshot id, dimensions and elapsed milliseconds at completion. It can
be inspected directly or encoded later with a video tool. Captures are
limited to 16 megapixels and four pending requests per session. Neither
pending screenshots nor recordings resume after a runtime restart.

Extensions can import =(techne editor)= and call =(screenshot! s path)=,
=(recording-start! s directory #:frames 30 #:interval 100)= and
=(recording-stop! s)=. The first returns a request id, not a completed
file. Pixel capture on a terminal frontend reports an explicit error:
the terminal emulator, not Techne, owns those pixels.

* Keys

A profile decides what keys mean. In the Emacs profile chords edit and
move, as in Emacs; in the modal profile keys work as in Vim, with
normal, insert and visual states, and Doom's leader key, =SPC=, in normal
state.

Some keys are prefixes: after one, the editor waits for the rest of the
sequence, and after a pause shows the keys that can follow, with what
they do (which-key). \[keyboard-quit] cancels whatever is pending.

Keys are looked up in the keymaps of the buffer's modes, most specific
first, then the profile's. \[describe-key] shows what a key runs and
where it is bound; \[describe-bindings] shows every key bound here.

* Files and buffers

A buffer is what you switch to: a file, a view the editor makes, the
REPL. \[find-file] opens a file, completing its name;
\[switch-to-buffer] switches to another buffer; \[kill-buffer] takes
one off the list; \[save-buffer] writes a file. The messages shown so
far are in *Messages*, \[view-echo-area-messages].

Saving is refused if the file changed on disk since it was read. The
message then names what you can do, and \[recover] asks which:
overwrite the file with the buffer's text, revert the buffer to the
file's (undo takes that back), or compare the two in *diff*. Each
expects the buffer as it was when the save was refused: once you edit
it again, save again. \[decisions] lists every failure still offering
choices; \[act-at-point] on one dismisses it.

* Files on other machines

A file on another machine is named as TRAMP names it: a route, then
its path there. =/ssh:build:/etc/hosts= is on build;
=/ssh:build|sudo:root@build:/etc/hosts= is the same file as root;
=/ssh:gw|ssh:build:~/src/= goes through gw. \[find-file] completes
such names a directory at a time, and typing goes on here: the file is
read when opened and written when saved, through a Techne node on the
other machine. Saving is refused if the file changed there since it
was read, as for a file here. Commands of the buffer's directory run
there: \[shell-command], \[async-shell-command], \[vc-status]. One
connection serves every file of a route, and one lost is made again
when next needed.

The node must be on the other machine, in =~/.cache/techne/bin= or on
its PATH (=remote-node-command=). ssh does not ask for passwords, nor
sudo: a key or an agent must do for ssh, and sudo must not need one.
Listing a remote directory (\[dired]) and searching a remote project
are not supported yet.

* Directories and the buffer list

\[dired] lists a directory, as Emacs's dired does; \[dired-jump] lists
the directory of this buffer's file, at the file. In a listing, RET
goes into a directory or opens a file and ^ goes up. Entries are marked
with m, flagged for deletion with d and unmarked with u; D, R and C
delete, rename (or move) and copy the marked ones, or the one at
point, and x deletes the flagged ones; % m marks the entries matching
a regular expression. The buffers of files moved follow them, unsaved
edits and all; those of files deleted are killed unless they have
unsaved edits. ( hides the details, . the dotfiles, s sorts by name,
time or size. C-x C-q makes the names editable in place, as wdired
does: C-c C-c renames what changed, also names swapped.

\[dirvish] shows a directory as dirvish does, in three panes: the
parent directory, the directory and a preview of the entry at point,
which follows the caret. Opening a file, or q, puts the panes back.

\[ibuffer] lists the buffers, as ibuffer does, grouped by project.
The same keys mark them; D kills the marked ones, S saves them; s
sorts, / n and / m filter by name and mode, / / shows all again.

* Editing

Commands act on every range of the selection. Motions move the caret by
characters, words, lines and the whole buffer; with a region active they
extend it. ~kill-region~, ~copy-region-as-kill~ and ~yank~ cut, copy and
paste through the kill ring, which the system clipboard joins;
\[yank-pop] chooses an older kill, previewing it in place. ~undo~ and
~redo~ go through the document's history, which survives a crash.

\[isearch-forward] searches as you type. In the Emacs profile, while it
searches, C-y, C-w and M-s C-e add the last kill, the next word or the
rest of the line to the search string, M-y an older kill instead,
M-p and M-n go through the earlier searches and M-e edits the string
in the minibuffer; any other key ends the search. \[search-lines] shows the
matching lines in the minibuffer, previewing each. \[search-project]
shows the matching lines of every file of the project, its
version-control root, as you type: a service of its own searches them,
so a large project holds up neither keys nor frames.

In the modal profile / and : read their line in the minibuffer, with
its keys and Vim's: DEL with nothing typed leaves it, C-w deletes a
word, C-r " puts the register. / highlights the matches as you type,
n goes to the next; : completes the editor's commands. M-p and M-n go
through what each read before.

Where the buffer's mode indents, \[newline-and-indent] indents the line
it opens and \[indent-for-tab-command] the line, or the region's lines;
\[indent-region] indents the region, \[back-to-indentation] goes to the
line's indentation. In the modal profile, = indents what a motion
covers, doubled the line.

* Panes

\[split-window-below] and \[split-window-right] split the focused pane;
\[other-window] focuses the next; \[delete-window] closes the focused
one, \[delete-other-windows] all others.

* The minibuffer and targets

The minibuffer reads a choice: typing narrows the candidates, the words
typed matching in any order; the selected candidate is previewed where
that makes sense. \[execute-extended-command] runs any command by its
name.

\[minibuffer-previous-history] and \[minibuffer-next-history] go
through what was taken before at the same kind of prompt: the commands
run by name, the files found, the words searched for, the shell
commands and the expressions evaluated. Going back past the newest
entry brings back what was typed. The commands and files taken before
are listed first, the last first. The histories are kept across runs,
as Emacs's savehist keeps them, in ~/.local/state/techne/history (under
$XDG_STATE_HOME when it is set).

What a candidate stands for, or the text at point, is a target: a file,
a buffer, a command, a location, a name. \[act-at-point] offers the
actions on it, in the minibuffer as on the text; RET does the first.
\[minibuffer-export] makes the candidates that are locations a lens.

* Compiling

\[compile] runs a command in the project's root, its version-control
root, and shows its output in *compilation* as it comes; the project
remembers the command, which \[recompile] runs again. The lines naming
a place in a file as compilers write it, file:line:column, are
highlighted: RET on one goes there in another pane, and \[next-error]
and \[previous-error] go to the next and the one before from anywhere.
\[kill-compilation] stops the command.

* Lenses and views

A lens shows parts of other buffers between labels. \[lens-search]
shows the lines containing a string in every buffer; editing a line
there edits its buffer. An edit the lens cannot make, because its
source changed since or it would change a label, is refused with the
reason.

A view is a lens of rows the editor makes: the inspector, help,
checkdoc. RET on a row does the default action on what it stands for.

* Command arguments and staged changes

\[command-form] chooses a command with a contract and opens its arguments
without running it. Its source pane supplies point, the region and buffer;
number keys 1 through 0 edit the first ten arguments, and \[form-edit]
edits the row at point. \[form-clear] clears it (omitting an optional
argument). Changing an argument rechecks later arguments' types.
\[form-apply] validates and applies; \[form-stage] stages document edits
as proposals, leaving source text and undo unchanged. Settings and external
effects cannot be staged, nor the edits of a command whose contract does
not declare that its body tolerates staging (it would see the old text,
not its own edits); renaming through a language server declares it.

\[operations] lists recorded operations. Inspect one to see its arguments,
outcome and changes; its ~again-operation~ action fills the argument form
from its record. References are checked again; sensitive or shortened
arguments must be entered again. A changed definition or contract is shown
for review rather than silently replayed.

A staged operation's ~proposals~ row opens read-only diffs.
\[accept-reviewed-proposals] accepts all as shown, as one linked operation;
\[reject-reviewed-proposals] rejects them. A changed document or proposal
set is refused: \[view-refresh] and review it again. A conflicting later
file changes neither; a journal failure part way is reported as partial.
Accepted edits remain unsaved, and undo of the accepting operation uses
its existing multi-document checks. Merging more edits replaces a proposal's
identity, so an old review cannot accept its new contents. Forgetting the
operation's kept record rejects any proposals still pending, changing no
source text; the record is otherwise kept, past the log's usual bounds,
while its proposals wait, so they do not vanish unreviewed. Pending proposals are not restored after restarting
the runtime.

* Modes and options

A buffer has one major mode, chosen by its file's name, and minor modes
that are on or off. A mode brings keys, highlighting and settings.
\[describe-mode] shows the modes of a buffer and their keys.

Options are declared settings, such as ~line-numbers~ and ~read-only~.
\[set-option] sets one in a buffer or globally; \[describe-option]
shows the settings that apply and which one wins.

* Lisp

Code is evaluated in its file's module, as it is in the file:
\[eval-defun], \[eval-last-sexp] and \[eval-buffer] in a Scheme
buffer, \[eval-expression] anywhere, and ~itl~, the REPL. A definition
evaluated replaces the old one at once, in a running editor.

A file is a module. ~(require "other.scm")~ loads another file's
module and imports what it ~provide~s, as Racket does: the editor's
Lisp is written so, and a package's files use each other so. A
library, defined with R7RS's ~define-library~ and named by a list such
as ~(srfi 1)~ or ~(techne crypto)~, is imported with ~import~: Techne's
libraries and portable Scheme come that way. Write your own code with
~require~; reach for ~define-library~ when it is to be imported by name.

\[xref-find-definitions] goes to the definition of the name at point, also of
the editor's own commands and of procedures written in Rust;
\[xref-go-back] comes back. \[inspect-at-point] inspects a value:
its type, documentation, definition and parts, each inspected in turn.

Lisp is indented as Emacs indents it: a form's body by two, the
arguments of a call under the first. \[indent-sexp] indents the form
around point. ~(set-indent! 'with-thing 1)~ makes a macro of yours
indent its first argument by four and its body by two, as Emacs's
scheme-indent-function property does; names starting with def have a
body already.

** Tracing Lisp

Import ~(techne debug)~ in the module whose procedures you want to trace:

#+begin_src scheme
(import (techne debug))
(trace compute)
(compute input)
(untrace compute)
#+end_src

~(trace)~ lists the bindings still traced; ~(untrace)~ stops all tracing.
Calls, results and raised conditions stream to the call's current output
port, including its nREPL request. Restarts remain live. An escape or
cancellation records an unwind; a killed task runs no cleanup and need
not record an exit.

The default log keeps 200 events, then suppresses further recording and
prints one limit notice. ~(clear-trace-log! (current-trace-log))~ discards
those events and rearms it. For a separate log without streamed output:

#+begin_src scheme
(define log (make-trace-log #:limit 100 #:port #f))
(parameterize ((current-trace-log log)) (compute input))
(trace-log-events log)
(trace-log-truncated? log)
#+end_src

Events are dicts with call and task numbers, nesting depth, phase,
module/name summaries and a bounded value summary. They do not keep
argument or result objects alive. Tasks sharing a log share its limit;
a new task starts at nesting depth zero. ~#f~ for ~current-trace-log~
disables tracing for that dynamic extent.

Tracing replaces a binding, not every reference to its old procedure.
Bindings are identified lexically, including through renamed imports,
not by the module of an evaluation calling an enable/disable procedure.
An earlier saved alias is not intercepted. Redefining the binding
replaces its wrapper: trace it again for the new definition. Untrace
never overwrites that new definition, and saved wrappers become
pass-through when retired. Guarded global JIT calls see the wrapper;
lexically inlined calls and sealed primitives are not intercepted.
Tracing collects returns, so it adds stack frames; after 32 nested
traced calls, deeper calls run without instrumentation. This is
observational tracing, not stepping or rollback, and its summaries may
contain sensitive data: trace only what you intend to disclose.

** Strings and Unicode performance

Strings are UTF-8. Character indexes count characters, not bytes.
~string-ref~ and ~string-length~ take constant time for ASCII and Unicode
strings alike: a sparse character index bounds how much UTF-8 is decoded
at any index. Scanning by increasing indexes is linear, including when a
long ASCII string contains just one non-ASCII character.

The index is built when a string is made and rebuilt when it is mutated;
mutation can take time proportional to the string's byte length. ASCII
strings keep their compact layout without an index; Unicode strings below
64 bytes use bounded decoding. Longer non-ASCII strings reserve a
character-count word and one index word per 64 bytes. The index
moves and is freed with the string, without a separate persistent cache.

For a linear scan, use ~string-for-each~ or the cursors of ~(srfi 130)~:

#+begin_src scheme
(import (srfi 130))
(let ((end (string-cursor-end text)))
  (let loop ((cursor (string-cursor-start text)))
    (unless (string-cursor=? cursor end)
      (write-char (string-ref/cursor text cursor))
      (loop (string-cursor-next text cursor)))))
#+end_src

Reading and advancing a cursor take constant time per character.
~substring/cursors~ copies a range without scanning from the beginning.
Start with ~string-cursor-start~ for a cursor; SRFI 130 also accepts
character indexes, but cursors avoid the index lookup. A cursor belongs
to the string it came from and must not be reused after mutation.

** Hash-table iteration

~(hash-table-for-each proc table)~ calls ~proc~ with each key and value.
Techne also accepts its older table-first order. It is a Techne extension,
available through ~(techne)~, not an export of ~(srfi 69)~. Portable
SRFI 69 code uses ~(hash-table-walk table proc)~ instead; SRFI 113's
procedure-first adapter is private to that library.

** Tools for callers

~techne tool --help~ gives a short orientation and signatures;
~techne tool ROOT~ gives the same help in a persistent project session.
Request ~(tool-help 'recipes)~ for runnable examples or ~(tool-help 'guide)~
for detailed contracts and limits; neither is dumped by default.
~techne tool ROOT FORM [SESSION]~ evaluates one Scheme form with ~project~
bound. The library is ~(techne tools)~, also usable in scripts and nREPL.

#+begin_src scheme
(tool-help)
(tool-help (quote tool-read))
(tool-help "read symbol")
#+end_src

Help comes from live bindings, not a separate manual or command catalog.
The tools operate on disk files, not unsaved editor buffers.

~techne tool --text ROOT FORM [SESSION]~ displays strings directly and
automatically renders disk-source read/expand replies with their original
line numbers, including flat result lists containing such replies. Other
values stay written as Scheme data; arbitrary ~path~/~text~ records and
process-output labels are not treated as files. Omit ~--text~ for structured
results, or use ~tool-show~ explicitly to format other kinds of replies.

~tool-show~ numbers source views by default: one header gives the filename,
full revision and ~file-lines~, then ~LINE: TEXT~ lines retain original source
coordinates. The header scopes the whole block, including search context and
snapshot expansion; full paths are not repeated on every source line. Separate
blocks, even in batches, keep their own header. Wrapped display lines must not
be mistaken for source coordinates. Use ~#:numbered #f~ for the old plain-text view.
A read's handle identifies only its selected region, not the entire file.
~region-complete~ says that region was returned fully; ~file-eof~ says
that the returned text reaches file EOF. If ~next~ is present, expand
that character offset first. Otherwise ~next-line~, when present, is the
next source line to pass to ~tool-read~. Do not count newlines yourself:
character clipping may end inside a line. ~file-lines~ is the file's real
line count (an empty file still has line 1). File-specific metadata and
~next-line~ are false for kept process output: its label is not a disk
path, and expansion finishes a region, not necessarily a running stream.

Search replies provide exact source lines and ~total~ matching lines.
Use ~#:before~ and ~#:after~ (0 to 8 each) for numbered context from the
same immutable snapshot, without a second disk read. The original hit
handle still covers one line; ~context-handle~ covers the requested
context. ~#:chars~ bounds context characters across the whole reply
(1 to 16000), not per hit. Check ~context-truncated~; when context was
requested, a ~#f~ context means the budget ran out. Its ~context-handle~
can still be expanded.

Search automatically attaches the innermost named definition for recognized
code at each hit's actual character position. ~#:enclosing #f~ opts out;
~#:enclosing #t~ also requests diagnostics for unsupported languages. Its ~enclosing~ record has a name, scope,
span and handle: expand that handle to read the whole definition without
rediscovering it by name. The definition uses the same immutable source
and parser as ~tool-symbols~. ~enclosing-complete~ and ~enclosing-status~
distinguish known absence from unavailable/partial syntax; a partial
owner is only a candidate. Ownership is syntactic, not semantic reference
resolution. One form defining multiple names uses the first enumerated
name for its shared span. Counts grouped by path cannot request owners.

~(tool-search project "literal" #:group-by 'path)~ instead returns
~path~/~revision~/~count~ items for matching files. ~total~ still counts
matching lines, not occurrences; ~files~ counts matching files and
~next~ pages files. Grouped queries do not cache source handles. Counts
cover the scan, not just the page: always check ~complete~, ~skipped~ and
~problems~ before treating them as full-repository totals. Context and
grouping cannot be combined. ~tool-show~ renders both modes directly.
Zero-hit rendering echoes the literal query, prefix and scanned text-file
count, and explains that regex operators are not interpreted. Alternatives
can be issued as separate literal queries in one Scheme batch. Structured
replies identify ~match-mode~ as ~literal~; ~query~ and ~prefix~ echoes are
bounded to 240 characters, with explicit truncation flags. A zero count in
an incomplete scan is still not proof that the full scope has no matches.

~(tool-cite project "FILE" #:from 10 #:to 20)~ validates an inclusive
source range and returns ~valid~, ~file-lines~, a canonical ~citation~
string and the revision checked. An optional ~#:revision~ rejects stale
reads. Past-end and stale-revision results are data, not CLI errors:
check ~valid~. Invalid arguments, missing files and binary files are errors.
Checks do not populate the source cache. A valid bound does NOT establish
that a claim is supported by those lines or that the disk stays unchanged.

For a known small file, prefer ~tool-read~ directly; defaults now fill its
bounded 200-line, 16000-character read. For a known definition, use
~tool-read-symbol~ directly. Use ~tool-symbols~ to discover names, not as a
mandatory preliminary read: pages default to an 8000-character rendered-label
budget with a 50-item ceiling. ~#:chars~ (1 to 16000) and ~#:limit~ (1 to 50)
can narrow these; ~next~ remains an item offset, not a character offset. A first
oversized item is returned alone so the cursor advances, marked ~budget-exceeded~.
~characters~ counts rendered labels plus their joining newlines; full structured
metadata and pagination notes are not part of that budget.

Prefer these queries to writing a source scanner. Small session helpers can reuse them;
~tool-help~ finds available bindings before you reimplement one.

* Help

Everything the editor defines says what it is:

- \[describe-function] a procedure, macro or command: its signature,
  where it is defined, its documentation and keys;
- \[describe-variable] a variable or an option;
- \[describe-symbol] any name, whatever it is;
- \[describe-command] a command;
- \[describe-key] what a key runs and why;
- \[describe-mode] and \[describe-bindings] the keys here;
- \[where-is] which keys run a command;
- \[apropos] every name containing the words typed;
- \[view-manual] this manual.

Help is a view: RET on a name describes it, RET on a definition goes
there, \[help-back] goes back.

* Extending

The editor's own commands, modes and keys are written with the same
interface extensions use, the library ~(techne editor)~:

#+begin_src scheme
(import (techne editor))

(define-command (shout-region s n)
  "Make the text of the region upper case."
  (replace-region! s string-upcase))

(define-key! emacs-map "C-c u" 'shout-region)
#+end_src

~define-command~ defines a command, here one replacing the text of the
region by what ~string-upcase~ makes of it; ~define-key!~ binds a key;
~define-mode~ and ~define-minor-mode~ define modes, ~define-option~ an
option, ~define-hook~ and ~add-hook!~ events and what reacts to them,
~define-action~ an action on targets and ~define-view~ a view. A package
loaded can be unloaded: what it defined goes with it.

* Documentation

Every name a module provides, and every command, mode, option and hook,
has a docstring; checkdoc and the language server say when one is
missing or breaks the convention, which is Guile's and Emacs's:

- the first line is a complete sentence of at most 72 characters,
  because lists of names show only it;
- a procedure says what it does in the imperative, "Return", not
  "Returns", and names each parameter in upper case;
- lines are at most 80 characters, continuation lines in the first
  column;
- keys are written ~\\=\[command]~ in a docstring's source, never as
  key names, so that each user reads the key of their own profile;
- other names, and code, are written in backquotes.

A procedure's docstring comes before its body, a macro's after the
literals of its ~syntax-rules~, a variable's after its value:

#+begin_src scheme
(define (twice x)
  "Return X doubled."
  (* 2 x))

(define-syntax swap!
  (syntax-rules ()
    "Swap the values of the variables A and B."
    ((_ a b) (let ((t a)) (set! a b) (set! b t)))))

(define tab-width 8 "Columns between tab stops.")
#+end_src

\[checkdoc] shows what is wrong in the code loaded, each problem at its
definition.
