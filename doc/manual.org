#+title: The Techne Manual

Techne is an editor you extend and inspect in its own Lisp while it
runs, in the spirit of Emacs. This manual says how to use it; what each
command, procedure, option and mode does is in the editor itself, where
help shows it (see [[*Help]]). Keys are shown as your profile binds them:
read here in the editor, \[find-file] is the key that opens a file.

* Starting

~techne FILE~ opens FILE in a window, ~techne term FILE~ in a terminal.
Both take ~--modal~ for the modal profile, Vim's keys; without it the
keys are Emacs's.

Edits are written to a journal as you make them. If the editor stops
before you save, the next start replays them: nothing typed is lost. A
crashed runtime is restarted at once with its files, panes and carets.

An editor running opens files for other programs, as Emacs's server
does for emacsclient: ~techne --open FILE~ (or ~techne term --open
FILE~) shows FILE in it and returns. With ~--wait~ it returns only once
you are done with the file: \[server-edit] saves it and kills its
buffer, as killing the buffer or =:wq= in the modal profile do. So
~EDITOR="techne --wait"~ edits commit messages in the editor you have
open. With no editor running, the command starts one on the file.

* Keys

A profile decides what keys mean. In the Emacs profile chords edit and
move, as in Emacs; in the modal profile keys work as in Vim, with
normal, insert and visual states, and Doom's leader key, =SPC=, in normal
state.

Some keys are prefixes: after one, the editor waits for the rest of the
sequence, and after a pause shows the keys that can follow, with what
they do (which-key). \[keyboard-quit] cancels whatever is pending.

Keys are looked up in the keymaps of the buffer's modes, most specific
first, then the profile's. \[describe-key] shows what a key runs and
where it is bound; \[describe-bindings] shows every key bound here.

* Files and buffers

A buffer is what you switch to: a file, a view the editor makes, the
REPL. \[find-file] opens a file, completing its name;
\[switch-to-buffer] switches to another buffer; \[kill-buffer] takes
one off the list; \[save-buffer] writes a file. The messages shown so
far are in *Messages*, \[view-echo-area-messages].

* Files on other machines

A file on another machine is named as TRAMP names it: a route, then
its path there. =/ssh:build:/etc/hosts= is on build;
=/ssh:build|sudo:root@build:/etc/hosts= is the same file as root;
=/ssh:gw|ssh:build:~/src/= goes through gw. \[find-file] completes
such names a directory at a time, and typing goes on here: the file is
read when opened and written when saved, through a Techne node on the
other machine. Saving is refused if the file changed there since it
was read, as for a file here. Commands of the buffer's directory run
there: \[shell-command], \[async-shell-command], \[vc-status]. One
connection serves every file of a route, and one lost is made again
when next needed.

The node must be on the other machine, in =~/.cache/techne/bin= or on
its PATH (=remote-node-command=). ssh does not ask for passwords, nor
sudo: a key or an agent must do for ssh, and sudo must not need one.
Listing a remote directory (\[dired]) and searching a remote project
are not supported yet.

* Directories and the buffer list

\[dired] lists a directory, as Emacs's dired does; \[dired-jump] lists
the directory of this buffer's file, at the file. In a listing, RET
goes into a directory or opens a file and ^ goes up. Entries are marked
with m, flagged for deletion with d and unmarked with u; D, R and C
delete, rename (or move) and copy the marked ones, or the one at
point, and x deletes the flagged ones; % m marks the entries matching
a regular expression. The buffers of files moved follow them, unsaved
edits and all; those of files deleted are killed unless they have
unsaved edits. ( hides the details, . the dotfiles, s sorts by name,
time or size. C-x C-q makes the names editable in place, as wdired
does: C-c C-c renames what changed, also names swapped.

\[dirvish] shows a directory as dirvish does, in three panes: the
parent directory, the directory and a preview of the entry at point,
which follows the caret. Opening a file, or q, puts the panes back.

\[ibuffer] lists the buffers, as ibuffer does, grouped by project.
The same keys mark them; D kills the marked ones, S saves them; s
sorts, / n and / m filter by name and mode, / / shows all again.

* Editing

Commands act on every range of the selection. Motions move the caret by
characters, words, lines and the whole buffer; with a region active they
extend it. ~kill-region~, ~copy-region-as-kill~ and ~yank~ cut, copy and
paste through the kill ring, which the system clipboard joins;
\[yank-pop] chooses an older kill, previewing it in place. ~undo~ and
~redo~ go through the document's history, which survives a crash.

\[isearch-forward] searches as you type; \[search-lines] shows the
matching lines in the minibuffer, previewing each. \[search-project]
shows the matching lines of every file of the project, its
version-control root, as you type: a service of its own searches them,
so a large project holds up neither keys nor frames.

Where the buffer's mode indents, \[newline-and-indent] indents the line
it opens and \[indent-for-tab-command] the line, or the region's lines;
\[indent-region] indents the region, \[back-to-indentation] goes to the
line's indentation. In the modal profile, = indents what a motion
covers, doubled the line.

* Panes

\[split-window-below] and \[split-window-right] split the focused pane;
\[other-window] focuses the next; \[delete-window] closes the focused
one, \[delete-other-windows] all others.

* The minibuffer and targets

The minibuffer reads a choice: typing narrows the candidates, the words
typed matching in any order; the selected candidate is previewed where
that makes sense. \[execute-extended-command] runs any command by its
name.

\[minibuffer-previous-history] and \[minibuffer-next-history] go
through what was taken before at the same kind of prompt: the commands
run by name, the files found, the words searched for, the shell
commands and the expressions evaluated. Going back past the newest
entry brings back what was typed. The commands and files taken before
are listed first, the last first. The histories are kept across runs,
as Emacs's savehist keeps them, in ~/.local/state/techne/history (under
$XDG_STATE_HOME when it is set).

What a candidate stands for, or the text at point, is a target: a file,
a buffer, a command, a location, a name. \[act-at-point] offers the
actions on it, in the minibuffer as on the text; RET does the first.
\[minibuffer-export] makes the candidates that are locations a lens.

* Compiling

\[compile] runs a command in the project's root, its version-control
root, and shows its output in *compilation* as it comes; the project
remembers the command, which \[recompile] runs again. The lines naming
a place in a file as compilers write it, file:line:column, are
highlighted: RET on one goes there in another pane, and \[next-error]
and \[previous-error] go to the next and the one before from anywhere.
\[kill-compilation] stops the command.

* Lenses and views

A lens shows parts of other buffers between labels. \[lens-search]
shows the lines containing a string in every buffer; editing a line
there edits its buffer. An edit the lens cannot make, because its
source changed since or it would change a label, is refused with the
reason.

A view is a lens of rows the editor makes: the inspector, help,
checkdoc. RET on a row does the default action on what it stands for.

* Modes and options

A buffer has one major mode, chosen by its file's name, and minor modes
that are on or off. A mode brings keys, highlighting and settings.
\[describe-mode] shows the modes of a buffer and their keys.

Options are declared settings, such as ~line-numbers~ and ~read-only~.
\[set-option] sets one in a buffer or globally; \[describe-option]
shows the settings that apply and which one wins.

* Lisp

Code is evaluated in its file's module, as it is in the file:
\[eval-defun], \[eval-last-sexp] and \[eval-buffer] in a Scheme
buffer, \[eval-expression] anywhere, and ~itl~, the REPL. A definition
evaluated replaces the old one at once, in a running editor.

A file is a module. ~(require "other.scm")~ loads another file's
module and imports what it ~provide~s, as Racket does: the editor's
Lisp is written so, and a package's files use each other so. A
library, defined with R7RS's ~define-library~ and named by a list such
as ~(srfi 1)~ or ~(techne crypto)~, is imported with ~import~: Techne's
libraries and portable Scheme come that way. Write your own code with
~require~; reach for ~define-library~ when it is to be imported by name.

\[find-definition] goes to the definition of the name at point, also of
the editor's own commands and of procedures written in Rust;
\[pop-definition] comes back. \[inspect-at-point] inspects a value:
its type, documentation, definition and parts, each inspected in turn.

Lisp is indented as Emacs indents it: a form's body by two, the
arguments of a call under the first. \[indent-sexp] indents the form
around point. ~(set-indent! 'with-thing 1)~ makes a macro of yours
indent its first argument by four and its body by two, as Emacs's
scheme-indent-function property does; names starting with def have a
body already.

* Help

Everything the editor defines says what it is:

- \[describe-function] a procedure, macro or command: its signature,
  where it is defined, its documentation and keys;
- \[describe-variable] a variable or an option;
- \[describe-symbol] any name, whatever it is;
- \[describe-command] a command;
- \[describe-key] what a key runs and why;
- \[describe-mode] and \[describe-bindings] the keys here;
- \[where-is] which keys run a command;
- \[apropos] every name containing the words typed;
- \[view-manual] this manual.

Help is a view: RET on a name describes it, RET on a definition goes
there, \[help-back] goes back.

* Extending

The editor's own commands, modes and keys are written with the same
interface extensions use, the library ~(techne editor)~:

#+begin_src scheme
(import (techne editor))

(define-command (shout-region s n)
  "Make the text of the region upper case."
  (replace-region! s string-upcase))

(define-key! emacs-map "C-c u" 'shout-region)
#+end_src

~define-command~ defines a command, here one replacing the text of the
region by what ~string-upcase~ makes of it; ~define-key!~ binds a key;
~define-mode~ and ~define-minor-mode~ define modes, ~define-option~ an
option, ~define-hook~ and ~add-hook!~ events and what reacts to them,
~define-action~ an action on targets and ~define-view~ a view. A package
loaded can be unloaded: what it defined goes with it.

* Documentation

Every name a module provides, and every command, mode, option and hook,
has a docstring; checkdoc and the language server say when one is
missing or breaks the convention, which is Guile's and Emacs's:

- the first line is a complete sentence of at most 72 characters,
  because lists of names show only it;
- a procedure says what it does in the imperative, "Return", not
  "Returns", and names each parameter in upper case;
- lines are at most 80 characters, continuation lines in the first
  column;
- keys are written ~\\=\[command]~ in a docstring's source, never as
  key names, so that each user reads the key of their own profile;
- other names, and code, are written in backquotes.

A procedure's docstring comes before its body, a macro's after the
literals of its ~syntax-rules~, a variable's after its value:

#+begin_src scheme
(define (twice x)
  "Return X doubled."
  (* 2 x))

(define-syntax swap!
  (syntax-rules ()
    "Swap the values of the variables A and B."
    ((_ a b) (let ((t a)) (set! a b) (set! b t)))))

(define tab-width 8 "Columns between tab stops.")
#+end_src

\[checkdoc] shows what is wrong in the code loaded, each problem at its
definition.
